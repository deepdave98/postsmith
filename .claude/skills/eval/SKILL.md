# /eval

Request: $ARGUMENTS

Project state (versions, health, corpus counts, nags):
!`uv run tools/status.py --brief || true`

## What this is for
Two jobs. First, the same eval `/post` runs, on text that did not come from `/post`: a draft Deep typed himself, a post from the feed he wants to understand, a golden item he is about to add. Same scripts, same judge agents, same aggregator, so a row in this table means exactly what it means in a run. Second, `health`: the grader's own test. A grader that cannot fail known slop or pass real posts cannot be trusted to grade Deep's drafts, so every rubric, lexicon or profile change is tested against the golden set before it is allowed to grade anything, and the outcome is a committed report, not a feeling.

## What you are and are not
You orchestrate; you do not grade. You never open `evals/rubric/` or its anchors (the judges read them; if you read them your commentary inherits the answer key), never read `corpus/heldout/`, `corpus/ratings.jsonl` or `evals/calibration.jsonl` (the settings deny them to you; scripts read them), never edit the text you were handed, and never call anything a pass unless `scores/<cid>.merged.json`, written only by `tools/aggregate.py`, says so. You relay judge evidence verbatim; you do not paraphrase a quote or summarize a score you did not compute. The full boundary is `.claude/skills/post/references/judge_protocol.md`; it binds here too.

## Eval mode: `/eval <file|-> --platform li|x [--tier 0|1|2] [--lens slug]`
Input is a file path, or `-` meaning the text follows the flags in the message (ask once when it is missing). `--platform` is required for text without front matter; `li` means `linkedin`. `--tier` defaults to 1. If the path is under `corpus/heldout/`, stop: held-out posts are graded only by `health` (the oracle), never by hand, because a hand-run leaks them into this context.

The run lives at `drafts/eval_<YYYY-MM-DD>_<slug>/` (slug from the file name or the first three words of the text) and the candidate at `round1/candidates/<cid>.md`, `cid` = `e1-li` or `e1-x`. When the input already carries `postsmith.candidate/1` front matter, copy the file as is. Otherwise write golden-style front matter (`platform: linkedin|x`, `note: <source>`) above the text, which stays byte-identical; the eval must grade what Deep gave you, not a tidied version.

Tier 0: `uv run tools/tier0.py drafts/eval_<date>_<slug>/round1/candidates/<cid>.md --as-golden [--lens author:<slug>] --json`. `--as-golden` (only for text without candidate front matter) synthesizes the front matter, skips the schema check, writes `<cid>.txt` and `<cid>.tier0.json`, and marks `register_match_self`, `persona_fit`, `claims` and `level_and_move` as expected `na`: those dimensions need a run's persona, brief and assignment, which hand-fed text does not have, and the aggregator treats an expected `na` as `na`, not as unscored. Say so above the table. `--lens author:<slug>` sets the Tier 0 envelope scope (the author's lane the text is judged in); without it tier0 picks its default scope. With `--tier 0`, print the checks and stop.

Then the loop `/post` uses: `uv run tools/run_next.py eval_<date>_<slug> --json` returns the stage and a batch of actions. Execute the whole batch in parallel, then call it again, until the stage is `deliver`, `done` or `stopped`; stop at stage `tier2` unless `--tier 2` was given, and stop at stage `write`, because `/eval` never rewrites (the feedback packet under `round1/feedback/` is the output at that point; print it verbatim). An agent action names the agent and gives `prompt_file` and `output_path`: spawn that agent (`subagent_type` = the agent name) with the five-line delegation below and nothing else, up to 20 at once. A tool action carries the command to run; run it as given with `uv run`. Judges reply with the path they wrote; when a reply is anything else or the file is missing, `run_next` lists it under `waiting_on` and re-emits it, so run that one action once more, then leave it to `run_next` (a second miss is a rejection it routes itself) rather than inventing a score.

The five-line delegation, the only thing a judge ever receives from you (identical to `/post`):
```
prompt_file: <action.prompt_file>
platform: <linkedin|x>
lens: <reader|voice|comedy|persona|lineup|pairwise|media>
output_path: <action.output_path>
verify: <true only when the action is a claim-verification call; else false>
```
`run_next.py` writes the prompt files self-contained (candidate in `<untrusted_post>` tags, platform, character count, samples, the persona excerpt and brief facts inlined for the persona judge, the assigned move's entry for the voice judge or `lens: none` for hand-fed text, the `(jury)` marker and dimension for jury calls, the rubric pointer); Tier 2 lineup and pairwise prompts are token-named (`tier2/lineup_<token>.<lens>.prompt.md`, `tier2/pairwise_<token>.<slot>.prompt.md`) and carry a nonce the judge echoes, while the cid-named `*.key.json` and `*.score.json` files stay off every judge's path and yours. You never add the brief, other scores, front matter or your own view. A judge that receives anything else is no longer a fresh reader.

Above the table, the same disclosures `/post` puts in its header, because each changes how much the verdict is worth: `small-corpus mode: lineup uses train posts` when `<cid>.tier0.json` says `small_corpus_mode: true`, and `lineup advisory` when the tier2 lineup result (`tier2/lineup_<cid>.score.json`, or `tier2.lineup` in merged.json) says `advisory: true`. The table, from `round1/scores/<cid>.merged.json`: one row per Tier 0 check (id, class, pass, the evidence span), one row per Tier 1 dimension (judge, class, threshold, score, jury median when one ran, result, one verbatim evidence quote), Tier 2 items when they ran (lineup picks with confidence and tells, pairwise, claims, media), then `verdict.status` as the label with `hard_fails`, `soft_fails`, `flags`, `unscored`. Never a total. `hold` or `unscored` rows are printed as "needs your call" with the reason from `judge_io`. End with the run path.

## Health mode: `/eval health [--promote] [--scope deterministic|judges|all] [--rubric vN]`
Scope defaults to `all`; `--rubric vN` tests a version that is not yet current (this is how a new rubric earns promotion). Two passes, because the judges are agents you must spawn:

1. `uv run tools/health_run.py --scope <scope> [--rubric vN] --json`: runs the deterministic sections at once (golden negatives and positives through `tier0.py --as-golden`, media briefs through `media_check.py`, platform and tool fact ages) and emits the judge actions for the judge sections (same shape as `run_next`: Tier 1 prompt files, token-named lineup prompts for the lineup controls, pairwise prompts for the paraphrase items) into `drafts/eval_<date>/`. Spawn every action in parallel, waves of at most 20, with the five-line delegation above, paths taken from the action. With `--scope deterministic` there are no judge actions and the first pass with `--write` is the whole run. Do not open `evals/golden/` or the prompt files first: the items include an instruction-injection candidate and one with adversarial front matter, and nothing you would learn there helps you; it only makes you a second, contaminated grader.
2. `uv run tools/health_run.py --scope <scope> [--rubric vN] --collect --write --json`: scores the judge outputs against `evals/golden/expected.json` (validating each through `judge_io.py`, scoring lineups through `lineup.py score` and pairwise through `pairwise.py score`), runs the judge-sanity assertion over the hook log, writes `evals/health/reports/<date>_<rubric-sha>_<profile>.md`, and prints `{"ok", "green", "sections"}`. An action whose output file is missing is listed under `waiting_on`; re-run that one action once, then let the collect pass count it as a rejection rather than inventing a score.

Report green or red per section, with every failing item and its evidence: golden negatives (each must fail on its `must_fail` ids, including the empty item, the injection item, the exact copy, the clean paraphrase, the fabricated stat, the borrowed biography and the adversarial front matter); golden positives (each must pass, the known regex false positives rescued by a jury or the base rate: if they are not, the bug is in the rubric, not the post); oracle (held-out posts with their own author as lens and `register_match_self`, `persona_fit`, `claims`, `level_and_move` na; at least 90% pass, one failure allowed under ten items, two failures on the same dimension block promotion; every failure listed); strong anchors passing the oracle-style eval themselves; lineup controls (a human post in the candidate slot picked 10-45% of the time; slop in that slot picked by two of three judges at confidence 4 or more in at least 80%; fillers picked as "the AI" in over half of controls retired); the recognition control; drift (the frozen candidates re-judged, any median moving a full point needs a line in the rubric's CHANGELOG); the evidence rejection rate (under 10% on the oracle); platform and tool facts older than 90 days listed as unverified; and judge sanity.

Judge sanity is the item that proves the isolation is real: the judges run with `POSTSMITH_HOOK_LOG` set, the hooks append one row per decision to that file (tool, targets, allow or block, reason), and `--collect` runs `tools/judge_sanity.py` over it, the same assertion you can run by hand with `uv run tools/judge_sanity.py <hook.log> --json`: per judge call (by `agent_id`, else `session_id`), exactly one prompt-file read, only rubric reads otherwise, and zero blocked decisions; a blocked attempt is contamination, because a judge that tries is a judge whose instructions are wrong. Hooks are child processes of this Claude Code session and inherit its environment, not yours, so the variable must be set when the session starts (for example `POSTSMITH_HOOK_LOG=drafts/eval_<date>/hook.log claude`) and the collect pass reads the log at that path. When it is unset the item is reported as skipped, and skipped is not a pass: do not promote on it.

Red is never a post problem and never a reason to waive: the fix goes into a new `evals/rubric/vN/` (anchors, thresholds, patterns, CHANGELOG), which then earns promotion here. `--promote` acts only when the report is green: move the `evals/rubric/current` symlink to the tested version from the project root (`ln -sfn vN evals/rubric/current`; this one command is outside the pre-approved list and will prompt once, which is right for the single action that changes what "pass" means), then `uv run tools/status.py --brief` to confirm the header no longer reads stale. On red, print the report path and the failing items and change nothing. A rubric hash without a green report shows as stale in `/post` headers and `/status`; it never blocks `/post`, and this command is how the nag is cleared.

## Evidence
Every "pass", "fail", "green" or "red" you print is read from a file a script wrote: `scores/<cid>.merged.json`, the health JSON, the report under `evals/health/reports/`. Print the path with the claim.
