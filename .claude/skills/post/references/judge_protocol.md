# Judge protocol for `/post` (and `/eval`, which uses the same judges)

Fresh-context judging only works if the judge's whole world is one file it did not choose. The orchestrator never
composes a judge's input; tools do (`run_next.py`, `lineup.py`, `pairwise.py`, `tier0.py`). This file says exactly
what crosses the boundary in each direction and what counts as a judgment.

## 1. What a judge receives: five lines, nothing else
```
prompt_file: drafts/<run>/round<k>/prompts/<cid>.<lens>.md      # Tier 2: tier2/lineup_<token>.<lens>.prompt.md, tier2/pairwise_<token>.<slot>.prompt.md,
                                                                #         tier2/claims_<cid>.prompt.md, media/<cid>.judge.prompt.md
platform: linkedin | x
lens: reader | voice | comedy | persona | media | lineup | pairwise
output_path: drafts/<run>/round<k>/scores/<cid>.<lens>.json    # Tier 2: tier2/lineup_<token>.picks/<lens>.json, tier2/pairwise_<token>.verdicts/<slot>.json,
                                                                #         tier2/claims_<cid>.json, media/<cid>.media-judge.json
verify: true | false                                            # true only for judge-persona claim verification at Tier 2
```
Every path comes from the `run_next` action; the orchestrator never constructs one. `<token>` is an opaque build
token (`lineup.lineup_token(run, cid, seed)`, `pairwise.pairwise_token(run, cid, mode)`, sha256 prefixes), so a
Tier 2 prompt file's name and header reveal no cid; the cid-named `tier2/lineup_<cid>.key.json`,
`tier2/pairwise_<cid>.exemplars.key.json` and every `*.score.json` are never handed to a judge and never opened by
the orchestrator. Each lineup and pairwise prompt ends with a per-slot `nonce` the judge copies into its output
file; `lineup.py score` and `pairwise.py score` discard a pick or verdict without the matching nonce.

The prompt file is self-contained and generated by `run_next.py` (Tier 1, juries, claims, media) or by
`lineup.py build` / `pairwise.py build` (Tier 2): a pointer to rubric §0 (the protocol), the dimension list for
this lens, the candidate text inside `<untrusted_post>` tags taken from `candidates/<cid>.txt` (post text only,
emitted by `tier0.py`; every wrapper tag inside it escaped by `common.escape_untrusted`), the platform, the
character count with "length is not quality", lettered exemplars where the dimension needs them (Posts A–C from
`corpus/self` for `register_match_self`; lens or common exemplars for `level_and_move`), and the output path.
The voice prompt inlines the assigned move's `style/moves.md` entry as `<move_entry>` (mechanism, trigger, shape,
execute_without_copying; never its `seen_in`); `level_and_move` is `na` only when the prompt says `lens: none`.
The persona prompt inlines `<persona_excerpt>` (the front-matter `can_claim`, `cannot_claim` and `do_not_target`
lists, numbered, plus the story bank, opinions held and refused, vocabulary use and never, claims and never
sections of `style/persona.md`), `<brief_facts>` (the brief's numbered `brief.fact#N` lines with text and URL, and
the `brief.user_detail` text) and the writer's claims as escaped JSON rows inside `<untrusted_claims>`; it names no
file under `style/`, and `judge-persona` never opens `style/persona.md` or the brief: the excerpt is the version
the run is graded against, and its hook denies `style/**`. Judges read the rubric themselves:
`evals/rubric/current/rubric.md` §0 and their dimension sections, plus
`evals/rubric/current/anchors/<dim>/{weak,strong}.md`.

## 2. What a judge never receives, and why
- The candidate `.md` front matter (assignment, angle sheet, claim sources, media intent, lineage): it is the
  writer's reasoning and a gaming channel ("device: brilliant deadpan, score 5"). Judges get the `.txt` only.
- `drafts/<run>/brief.md` and `brief_inputs.json`: the obvious-takes list would pre-empt the `uniqueness`
  pre-step. The only brief content that reaches any judge is the numbered fact lines and the user detail, inlined
  by `run_next.py` into the persona prompt so `claims` can tell `brief` and `user_provided` from `needs_check`;
  the obvious takes, the story-match reasoning and the scout's notes never cross.
- Feedback packets, earlier rounds, other judges' scores, jury votes, which candidate is a rewrite: independence
  is the product; a judge that knows what round it is grades the trajectory instead of the text.
- `*.key.json`, `*.score.json`, the cid behind a token-named Tier 2 prompt, which lineup slot or pair order holds
  the candidate, which text is human, any rating, `memory/**`, `evals/calibration.jsonl`, `evals/golden/**`,
  `evals/disagreements.jsonl`, `corpus/**` except the lettered exemplars inlined in the prompt file (a Grep over
  the corpus would identify lineup fillers by elimination), and the other lenses' prompt files or the writers'
  prompt files under `round<k>/writers/` (each judge's allow list names its own lens's prompt files only).
- Anything spoken by the orchestrator beyond the five lines: no "this one is the finalist", no "the writer used
  deadpan", no "be strict".
Judge hooks deny these paths and restrict Writes to the output path; `omitClaudeMd: true` keeps CLAUDE.md out of
the judge's context where supported. The orchestrator must not narrate around the hooks. A delivered run's prompt
files are archived under `drafts/<run>/archive/`, outside every allow list.

## 3. What counts as a judgment
A judgment exists only when the JSON is written to `output_path` and
`uv run tools/judge_io.py validate <judge.json> --candidate <cid>.txt` returns `ok: true`. A verdict spoken in a
judge's final message is not a judgment. Validation checks the schema (contracts §6), `rubric_version` against
`current`, integer scores, and that every scored dimension carries at least one `evidence[].quote` that matches
the candidate after normalisation (NFKC, quotes/dashes/ellipsis folded, whitespace collapsed, case-insensitive;
exact substring or difflib ratio ≥ config `evidence_fuzzy_ratio`). `na: true` needs no evidence but does need a
non-empty `pre_step` reason; `na` never fails. A full judgment must carry every dimension of its lens (a missing
one is rejected per dimension so the rerun ladder engages), and the file name is authoritative for the lens: a
body whose `lens` disagrees is rejected whole. Lineup picks and pairwise verdicts must echo the nonce their prompt
carried; `lineup.py score` and `pairwise.py score` discard a file without it, and when nothing valid remains they
return `ok: false`, which the orchestrator reports as a missing judgment, never as a pass.

## 4. Rerun with another lens
A rejected judgment is not retried with the same judge. `run_next.py` emits one rerun of the rejected dimensions
with a fresh judge of another lens (reader ↔ voice ↔ comedy rotation; persona reruns with voice), a regenerated
prompt file, and a new output path. A second rejection makes soft dimensions `na` by rejection (counted
separately in `judge_io.na_by_rejection`) and hard dimensions `hold`. Two or more `na`-by-rejection on one
candidate route it to `needs_your_call`; it can never pass on rejections. Health fails if the rejection rate on the
oracle exceeds 10%, so a high rejection rate is a rubric bug to report, not something to route around.

## 5. Jury composition
`aggregate.py` writes `jury_requests` when: a soft dimension scores exactly threshold − 1; a hard judged dimension
scores exactly 3; any `hold`; a known-false-positive regex hit (P8, P10, P12, P17); an O3 flag. A jury is the
original judgment plus two fresh judges from the other two lenses (three fresh judges for a `hold`), same
dimension, same anchors, differently worded lens framing (rubric §5); `config.judges.jury_diverse_models` may put
one on another model. The median decides; a split ≥ 2 is logged to `evals/disagreements.jsonl` by the tool. At most
three juries per candidate per round. A `hold` that survives a jury without valid evidence becomes `unscored` →
`needs_your_call`. Jury judges receive the same five lines as any judge; they are not told they are a jury or what
the first score was.

## 6. Turing lineup (Tier 2, top finalist per platform; both with `--wide`)
1. `uv run tools/lineup.py build <run> <cid> --seed N [--pool heldout|train]` (emitted by `run_next`) writes one
   prompt file per lens, `tier2/lineup_<token>.<lens>.prompt.md` (`<token>` = `lineup.lineup_token(run, cid,
   seed)`; the prompt names neither the cid nor another prompt file), with posts A–D anonymised (URLs, @handles,
   emails, bare domains, every token of the filler author's name and handle, and the persona's own name, aliases,
   brands and handle stripped; casing, emoji and line breaks kept; every post escaped inside its tag) in that
   lens's seeded order, ending with that lens's `nonce`. The cid-named `tier2/lineup_<cid>.key.json` records the
   candidate slot, the fillers, the seed, the token, the nonces, the prompt files, the picks directory and the
   per-lens orders; a rebuild wipes the picks directory. Fillers: three heldout posts, same platform, length ± 30%,
   three different authors, lower-engagement preferred; in small-corpus mode, train posts minus the candidate's
   `exemplars_seen`, and the header says so. Fewer than six eligible fillers marks the key and every prompt
   `advisory`.
2. Three `judge-lineup` calls, lens `reader`, `voice`, `comedy`, each with its five lines (paths from the action).
   The question is fixed in rubric §3: exactly one of the four was produced by an AI system; pick it, confidence
   1–5, the single strongest tell with a verbatim quote. Output `{"pick","confidence","tell","quote","nonce"}` to
   `tier2/lineup_<token>.picks/<lens>.json`; a pick without its nonce is invalid.
3. `uv run tools/lineup.py score <run> <cid>` merges the picks the key names into `tier2/lineup_<cid>.score.json`
   (`pass`, `picks`, `invalid`, `rule`, `advisory`). Fail if ≥ 2 picks land on the candidate at confidence ≥ 4, or
   all three pick it at any confidence. A single pick at ≥ 4 passes and its tell enters the next feedback packet.
   Nothing valid left → `ok: false`: a missing judgment, never a pass.
4. Optional, off by default: a one-judge lineup on every Tier-1-passing candidate, emitted by
   `run_next` only when config `run.quick_lineup_on_tier1_pass` is true; a pick at confidence ≥ 4 is a ranking
   flag, not a gate. While it is off, alternates are reported as "passed Tier 0-1, not lineup-tested" and no report
   header may imply otherwise. Fewer than the required eligible fillers → `lineup advisory`, stated in the header.
The key file and the score file are never on a judge's path; the orchestrator never opens the key either.

## 7. Pairwise and paraphrase
- **Exemplar paraphrase check (hard gate, every finalist):** `uv run tools/pairwise.py build <run> <cid> --mode
  exemplars` writes one prompt per order × exemplar against the two closest `lineage.exemplars_seen` (closest by
  archetype + hook type + ending + expectation-ledger shape) as `tier2/pairwise_<token>.<slot>.prompt.md`
  (`<token>` = `pairwise.pairwise_token(run, cid, mode)`; headers name the platform, never the cid; each slot ends
  with its own `nonce`) and the cid-named `tier2/pairwise_<cid>.exemplars.key.json`; a rebuild wipes the verdicts
  directory. `judge-pairwise` answers `same_post_rewritten` and `same_skeleton_or_joke` with the shared span,
  echoing the nonce, into `tier2/pairwise_<token>.verdicts/<slot>.json`; `uv run tools/pairwise.py score <run>
  <cid> --mode exemplars` merges the verdicts the key names (a verdict without its nonce is invalid) into
  `tier2/pairwise_<cid>.exemplars.score.json` and sets `paraphrase: true` if any judge says yes to either → the
  variant is dropped. This is the real copy risk: the writer saw exactly these posts.
- **O3-triggered check:** when Tier 0 flagged `O3_skeleton`, the same question runs against the nearest heldout
  post; yes = drop.
- **Reference pairwise (advisory ranking):** `pairwise.py build|score <run> <cid> --mode reference`, nearest
  heldout reference, both orders × lenses, the same token and nonce scheme (key `tier2/pairwise_<cid>.key.json`,
  score `tier2/pairwise_<cid>.score.json`), char counts shown with the length disclaimer; "which is the better
  post" and "which sounds more like the voice in Posts A–C" where A–C are Deep's self samples, not the lens
  author. Inconsistent answers across orders = tie. Skipped when the lineup is clean 0/3 (config
  `skip_pairwise_when_lineup_clean`). It never gates.

## 8. Claims verification and media
- `judge-persona` with `verify: true` receives `tier2/claims_<cid>.prompt.md`, listing the `needs_check` claims
  from the classification round (the judge still never sees the front matter itself). WebSearch per claim →
  `verified (url) | plausible | unverifiable | wrong`, written as a JSON array `[{text, status, source, url, why}]`
  to `tier2/claims_<cid>.json` (not a judge document; `run_next` folds it into `<cid>.tier2.json`). Any `wrong` is
  a hard fail; `unverifiable` about a named real company or person is needs confirmation, not a fail.
- `media-director` writes `drafts/<run>/media/<cid>.brief.yaml` and `media/<cid>.prompts/<tool>.md`;
  `uv run tools/media_check.py <brief> --prompts <dir>` (result at `media/<cid>.media-check.json`) gates schema,
  rule citation, aspect, text budgets, negations; `media-judge` then receives `media/<cid>.judge.prompt.md`
  (written by `run_next`: the brief, the rendered prompts and the caption as data) and writes the `media` dimension
  with its sub-results to `media/<cid>.media-judge.json`.

## 9. The orchestrator's part of the protocol
Spawn the agent named in the action with the five lines; wait; run `run_next` again. Never: open `evals/rubric/`
or the anchors; read a `*.key.json`; reorder, rewrite or annotate a prompt file; run a judge on a candidate the
batch did not name; accept a spoken verdict; paraphrase evidence when relaying a packet; tell any judge which text
is human, which is a rewrite, or what another judge said. If a hook blocks a judge, that is the protocol working:
report it in `run.log`, do not hand the judge the file another way.
